# ADR 0003: Bidirectional meals and idempotent workout ingestion

Status: app-side meal pull and correction merge implemented and device-cached; authenticated pull/retry verified on Simulator; complete HealthKit backfill and repeat device sync remain unverified.

The iPhone uploads HealthKit records, app-entered weight, and app-captured meals. A user-triggered ChatGPT/Codex session may instead create a meal and a separate nutrition estimate in Supabase; the app downloads both before starting a potentially long HealthKit backfill. A remote meal may have no stored image. The app caches source meals and estimates separately and computes daily estimated intake only from estimates matched by stable meal ID. Provisional values remain labeled estimates. No service-role/admin key belongs in the app or skill; a future meal writer must use a separately revocable owner-scoped authorization, with RLS verified before use.

Cloud meal rows are authoritative for an existing meal ID because the app has no meal-edit action. Reconcile metadata by stable ID on every pull, persisting a changed note or eaten time instead of skipping an existing ID. Keep the last remote image path with the cached meal and download an image only for a new or changed path; retries with the same ID/path are no-ops. A local app photo with its expected uploaded path is already cached. This does not detect replacement of image bytes at an unchanged Storage path, so a cloud writer must use a new path when replacing an image. The local regression test first reproduced a stale note after a cloud correction, then passed after the merge change; a second test covers path change and retry. The authenticated Simulator pulled existing cloud meals/estimates and repeated Refresh Meals without duplicates or changed totals. A live cloud correction to an existing meal has not been performed.

HealthKit record identity is `(user_id, external_id)` for samples and `(user_id, healthkit_id)` for workouts. Uploads use those unique conflicts for idempotent upserts. A batch anchor is persisted only after all its cloud writes succeed, so retries repeat the same stable IDs rather than creating duplicates. Deletes are additionally scoped by user ID.

The live `tracker_workout_duration` constraint requires a finite nonnegative duration no greater than `end_at - start_at`. One real HealthKit workout violated it and stopped the sync. Normalize workout boundaries outward to whole seconds, cap the uploaded duration to that interval, and retain the raw HealthKit duration and whether it was capped in `source_metadata`. This satisfies the live constraint without weakening it or discarding the workout. The mapping is deterministic across retries. The live schema already supports nullable meal images, `meal_estimates`, and `workouts.source_metadata`. Separately, after exporting all 3 meals and 3 estimates to a private local backup and checking for duplicate keys, `supabase/sql/20260927_meal_estimate_unique.sql` added a unique `(user_id,meal_id)` constraint. The post-migration check showed one such constraint and zero duplicate keys. No rows were deleted.

Verification gate: current-source real-device build/install, three existing remote meals and estimates visible in the authenticated Simulator, workout and sleep records uploaded, and two consecutive device syncs with unchanged row counts and stable IDs. The unsigned Simulator build skips HealthKit. Hourly background behavior requires later observation because iOS does not guarantee exact wake times.
